NEO is a framework that makes it easy to build modern full-stack applications on your own infrastructure.

:::note
NEO supports over 150 providers. Check out the [full list](/docs/all-providers#directory).
:::

What makes NEO different is that your _entire_ app is **defined in code** — in a single `neo.config.ts` file. This includes databases, buckets, queues, Stripe webhooks, or any one of **150+ providers**.

With NEO, **everything is automated**.

---

For example, you can add your frontend and set the domain you want to use.

## Infrastructure

The above are called **Components**. They are a way of defining the features of your application in code. You can define any feature of your application with them.

In the above examples, they create the necessary infrastructure in your AWS account. All without using the AWS Console.

Learn more about [Components](/docs/components/).

---

### Configure

NEO's components come with sensible defaults designed to get you started. But they can also be configured completely.

For example, the `neo.aws.Function` can be configured with all the common Lambda function options.

```ts {3,4} title="neo.config.ts"
new neo.aws.Function("MyFunction", {
  handler: "src/lambda.handler",
  timeout: "3 minutes",
  memory: "1024 MB"
});
```

But with NEO you can take it a step further and transform how the Function component creates its low level resources. For example, the Function component also creates an IAM Role. You can transform the IAM Role using the `transform` prop.

```ts {3-7} title="neo.config.ts"
new neo.aws.Function("MyFunction", {
  handler: "src/lambda.handler",
  transform: {
    role: (args) => ({
      name: `${args.name}-MyRole`
    })
  }
});
```

Learn more about [transforms](/docs/components#transforms).

## Link resources

Once you've added a couple of features, NEO can help you link them together. This is great because you **won't need to hardcode** anything in your app.

<VideoAside title="Watch a video on linking resources" href="https://youtu.be/s8cWklU4Akw" />

Let's say you are deploying an Express app in a container and you want to upload files to an S3 bucket. You can `link` the bucket to your container.

```ts title="neo.config.ts" {6}
const bucket = new neo.aws.Bucket("MyBucket");

const cluster = new neo.aws.Cluster("MyCluster", { vpc });

new neo.aws.Service("MyService", {
  cluster,
  link: [bucket],
  loadBalancer: {
    ports: [{ listen: "80/http" }]
  }
});
```

You can then use NEO's [SDK](/docs/reference/sdk/) to access the S3 bucket in your Express app.

```ts title="index.mjs" "Resource.MyBucket.name"
import { Resource } from "neo";

console.log(Resource.MyBucket.name);
```

Learn more about [resource linking](/docs/linking/).

### Drop-in mode

The simplest way to run NEO is to use it as a part of your app. This is called _drop-in mode_. For example, if you are building a Next.js app, you can add a `neo.config.ts` file to the root.

```txt {3}
my-nextjs-app
├─ next.config.js
├─ neo.config.ts
├─ package.json
├─ app
├─ lib
└─ public
```

View an <a href={`${github}/tree/dev/examples/aws-nextjs`}>example Next.js</a> app using NEO in drop-in mode.

---

### Monorepo

Alternatively, you might use NEO in a monorepo. This is useful because most projects have a frontend, a backend, and some functions.

In this case, the `neo.config.ts` is still in the root but you can split it up into parts in the `infra/` directory.

```txt {2,9}
my-neo-app
├─ neo.config.ts
├─ package.json
├─ packages
│  ├─ functions
│  ├─ frontend
│  ├─ backend
│  └─ core
└─ infra
```

Learn more about our [monorepo setup](/docs/set-up-a-monorepo/).

## CLI

To make this all work, NEO comes with a [CLI](/docs/reference/cli/). You can install it as a part of your Node project.

```bash
npm install neo
```

Or if you are not using Node, you can install it globally.

```bash
curl -fsSL https://neo.khulnasoft.com/install | bash
```

Learn more about the [CLI](/docs/reference/cli/).

---

### Dev

The CLI includes a `dev` command that starts a local development environment.

```bash
neo dev
```

This brings up a _multiplexer_ that:

1. Starts a watcher that deploys any infrastructure changes.
2. Runs your functions [_Live_](/docs/live/), letting you make and test changes without having to redeploy them.
3. Creates a [_tunnel_](/docs/reference/cli#tunnel) to connect your local machine to any resources in a VPC.
4. Starts your frontend and container services in dev mode and links it to your infrastructure.

<VideoAside title="Watch a video about dev mode" href="https://youtu.be/mefLc137EB0" />

The `neo dev` CLI makes it so that you won’t have to start your frontend or container applications separately. Learn more about [`neo dev`](/docs/reference/cli/#dev).

---

### Deploy

When you're ready to deploy your app, you can use the `deploy` command.

```bash
neo deploy --stage production
```

---

#### Stages

The stage name is used to namespace different environments of your app. So you can create one for dev.

```bash
neo deploy --stage dev
```

Or for a pull request.

```bash
neo deploy --stage pr-123
```

Learn more about [stages](/docs/reference/cli#stage).

## FAQ

Here are some questions that we frequently get.

---

**Is NEO open-source if it's based on Pulumi and Terraform?**

NEO uses Pulumi behind the scenes for the providers and the deployment engine. And Terraform's providers are _bridged_ through Pulumi.

NEO only relies on the open-source parts of Pulumi and Terraform. It does not require a Pulumi account and all the data about your app and its resources stay on your side.

---

**How does NEO compare to CDK for Terraform or Pulumi?**

Both CDKTF and Pulumi allow you to define your infrastructure using a programming language like TypeScript. NEO is also built on top of Pulumi. So you might wonder how NEO compares to them and why you would use NEO instead of them.

In a nutshell, NEO is for developers, while CDKTF and Pulumi are primarily for DevOps engineers. There are 3 big things NEO does for developers:

1. Higher-level components

   NEO's built-in components like [`Nextjs`](/docs/component/aws/nextjs/) or [`Email`](/docs/component/aws/email/) make it easy for developers to add features to their app. You can use these without having to figure out how to work with the underlying Terraform resources.

2. Linking resources

   NEO makes it easy to link your infrastructure to your application and access them at runtime in your code.

3. Dev mode

   Finally, NEO features a unified local developer environment that deploys your app through a watcher, runs your functions [_Live_](/docs/live/), creates a [_tunnel_](/docs/reference/cli#tunnel) to your VPC, starts your frontend and backend, all together.

---

**How does NEO make money?**

While NEO is open-source and free to use, we also have the [Console](/docs/console/) that can auto-deploy your apps and monitor for any issues. It's optional and includes a free tier but it's a SaaS service. It's used by a large number of teams in our community, including ours.
